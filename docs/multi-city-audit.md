# Multi-city audit — before implementation

Inspected the current working tree on 2 October 2026. It contains extensive pre-existing uncommitted changes; these are retained. No AGENTS.md instructions were found in the workspace or parent paths. No deployment, commit, push, or production data mutation is authorized.

## Public entry points and inventory

- `app/page.tsx` reads up to 20 legacy `countries/PK/cars` using Firestore Lite; `HomePageClient` then reads the collection again in the browser through `useCars`. Its only city option is Islamabad / Rawalpindi, encoded as `islamabad`; service is fixed to withDriver. Country options are fetched separately even though booking country is PK. Model cards group legacy cars and take minimum within-city daily rates. Homepage and city/detail filters differ.
- Islamabad and Rawalpindi pages use `CityVehicleSelector`: browser fetch of legacy cars, active/support flags, shared Twin Cities cityList, six priority models. Selection opens `ModelListingsBottomSheet`, which resolves vendor-backed cars; `CarDetailsModal` fetches vendor identity, displays it, and opens `LeadModal` with carId/vendorId/vendorName and package price.
- Twin Cities car routes independently read legacy cars and vendors, omit some active filters, and send vendor objects to `CarListingClient`. Routing uses the existing ten-model allowlist, Islamabad/Rawalpindi, and with-driver. Existing canonical URLs must remain stable.
- `/cars` is another legacy public entry point and must adopt the shared public presentation to prevent a residual vendor-selection path.
- Lahore page already uses server-only `resolveNormalRentalInventory({zoneId:'lahore',cityId:'lahore',service:'withDriver'})`. `toPublicLahoreInventory` strips vendor fields and hashes option IDs. `LahoreBookingClient` groups models, respects separate-card/public-label/year settings, displays minimum daily within-city price, and offers anonymous option comparison. Lahore model routes and sitemap use `getEligibleLahoreModels`/`getEligibleLahoreModel`.

## Actual sources of truth and eligibility

- `normal-rental/zones.ts` defines Twin Cities as legacy and Lahore as operations; both are publicly enabled. The existing resolver already loads legacy cars/vendors for Twin Cities and cars + zone-filtered `normalRentalInventory` + `normalRentalVendors` for Lahore.
- Lahore inventory stores modelSourceCarId, modelKey/name, vendorId, active, pricing.withDriver.{withinCity,outsideCity}.{daily,weekly,monthly}, optional image override/year/public label/separate-card flag. Legacy cars supply model definitions/images/specs, not Lahore rates. Disabling a legacy representative car is not a Lahore inventory deactivation: operational inventory.active is authoritative. No approved flag is used by this public resolver.
- Lahore requires active inventory, active same-zone vendor, existing model source with matching normalized key, and positive finite daily rates for both trip packages. Optional rates are finite numbers. There is no date-level vehicle availability lookup: this is supply eligibility, with final availability confirmed operationally.
- Twin Cities resolver requires an existing legacy vendor relationship, shared cityList eligibility, and car.active != false. Before migration it does not check vendor.active or service support, and requires both daily package rates. Browser paths have different filtering. Legacy vendor activation is optional; missing flags must retain compatibility. Explicitly inactive vendors and unsupported services should be excluded. There is no demonstrated approval-state contract for legacy vendors; do not invent one.
- `app/admin/pricing/_lib/operations.ts` reads and edits these same stores; Twin Cities edits legacy pricing fields, Lahore edits operational records. No new collection or duplicated price table is needed.

## Booking, tracking, operations

- Legacy LeadModal creates RK-ISL/RK-RAW counter-based IDs, writes leads directly from the browser with car/vendor/package/location fields, then invokes delivery with twin_cities_normal. Client ref prevents concurrent submissions. lead_submit and generate_lead follow persistence, plus existing Google Ads/Meta/WhatsApp calls. Vendor identity is also in public WhatsApp text and analytics.
- Lahore uses `/api/normal-rental-lead` and shared `lahore-lead.ts`; server re-resolves opaque IDs, checks the selected package rate, and atomically increments the existing counter and creates a lead. It stores raw inventoryId/vendorId/vendorName internally; public success omits vendor data. IDs are RK-LHR. Admin test route shares this core with authentication, raw IDs, and a fixed private source. Public source is fixed server-side. Client ref and IP rate limit exist; no durable request idempotency exists yet.
- Booking delivery uses leads, twin_cities_normal/lahore_normal, and the existing orchestration to email, Sheets, and dispatch. `dispatch/booking-adapters.ts` uses zoneId/city, carName/publicVehicleLabel, dates, locations, and estimatedRentalAmount. Assignment uses dispatch fleet/vendor/driver eligibility and vendor-first rules; it does not require customers to choose a vendor. Keep source carId for Twin Cities and inventoryId/vendor references on leads. Do not edit dispatch matching or finance.
- Homepage/city cards emit select_model + Meta ViewContent. City changes emit select_city. Homepage service is fixed (no select_service interaction). Existing detail/package/booking-intent tracking is in legacy components. Lahore emits generate_lead only after success. Preserve flow-specific conversion behavior; never add an additional Ads primary conversion. GTM/Meta/Clarity configuration stays untouched.
